# coverage-floors.txt — per-package coverage ratchet (GitHub issue #21).
#
# Format: one entry per line, "<go-package-import-path> <decimal-floor-percent>".
# Floors are ONE-DECIMAL values (e.g. "82.7"), not integers. Blank lines and
# lines starting with # are ignored; trailing "# ..." comments on a data
# line are also stripped.
#
# scripts/check-coverage-floors.sh (wired into `make coverage-check` and the
# ubuntu-latest leg of CI — see the Linux-only note below) fails the build
# when either:
#   - a package's CURRENT coverage falls below its floor here, or
#   - this file and `go list ./...` have drifted out of sync in EITHER
#     direction (a package with no floor entry, or a floor entry for a
#     package that no longer exists).
# The script computes each package's coverage itself from the raw
# `-coverprofile` data (covered statements / total statements), never from
# `go test -cover`'s own rounded percentage display — see the script's own
# header for why that distinction matters at one-decimal tolerance.
#
# TOLERANCE: 0.5 points, not 2. Floors are today's measured coverage MINUS
# 0.5, TRUNCATED (never rounded) to one decimal — e.g. a measured 83.2549%
# floors at 82.7, not 82.8 and not "83" from integer-flooring. This is
# deliberately tight: at the old 2-point/integer-tolerance scheme (up to
# ~2.25 points of real slack once integer-flooring was added in), a
# same-sized re-add of internal/cli/planreview.go itself (53 statements,
# 0% covered) would have needed 60 new uncovered statements in internal/cli
# before the gate caught it -- i.e. it would NOT have caught the exact file
# this ratchet exists because of. See "KNOWN LIMITATION" below for the
# current (tightened) numbers, which are much smaller but still nonzero.
#
# NOISE CHECK (performed before adopting 0.5): ran `go test ./... -cover
# -count=1` three consecutive times (count=1 forces real re-execution,
# bypassing Go's test-result cache, so this is genuine run-to-run
# variance) and compared each package's EXACT covered/total ratio (not the
# rounded display) across the three runs:
#   - 16 of 17 packages: bit-identical across all three runs (0.0000-point
#     spread) -- cmd/comrade, internal/audit, internal/config,
#     internal/context, internal/doctor, internal/engine,
#     internal/executor, internal/i18n, internal/llm, internal/redact,
#     internal/safety, internal/secrets, internal/shellinit, internal/tui,
#     internal/undo, internal/update.
#   - internal/cli: 83.2549% / 83.3960% / 83.2549% -- a genuine ~0.14-point
#     spread (a timing/scheduling-sensitive branch somewhere in its test
#     suite; not chased down further since it's well inside tolerance).
# All 17 packages' spreads are comfortably under the 0.3-point threshold
# that would have required an individually larger, documented tolerance
# for that package -- so a single blanket 0.5-point tolerance is used for
# every package below; none needed a special case.
#
# Re-baselining after intentionally changing a package's coverage:
#   1. go test ./... -coverprofile=/tmp/cov.out -covermode=set   (on Linux
#      -- see the note below on why; -count=1 a few times first if you
#      want to sanity-check noise for that package before trusting a
#      single run)
#   2. For the changed package, compute its exact percentage from the
#      profile (covered statements / total statements in that package's
#      files * 100 -- do NOT read this off `go test -cover`'s own rounded
#      display), subtract 0.5, and TRUNCATE (never round) to one decimal.
#   3. Never raise a floor above a package's ACTUAL current coverage — that
#      would make the gate fail immediately on the next unrelated commit.
#   4. Adding a brand-new package: add a line here in the same pass (the
#      guard above fails the build otherwise). A package with genuinely no
#      tests yet (e.g. a thin main-only package) gets floor 0.0 with a
#      comment explaining why, not a fabricated test.
#   5. If a package's floor is ever raised again, re-run the 3x `-count=1`
#      noise check above for it; if its spread now exceeds 0.3 points, give
#      it its own larger, individually documented tolerance instead of
#      forcing the blanket 0.5 — do not silently ship a gate that flakes.
#
# Linux-only, deliberately: every floor below was measured on ubuntu-latest,
# and CI only runs this check on the ubuntu-latest matrix leg (see the
# "Coverage floors" step's own comment in .github/workflows/ci.yml). Do NOT
# re-baseline from a macOS or Windows run — per-package coverage genuinely
# differs by OS in this repo (internal/executor and internal/shellinit
# branch on runtime.GOOS with only one branch executing per OS,
# internal/doctor/check_path.go is GOOS-aware, and several tests skip on
# Windows), so a macOS/Windows measurement would silently drift these
# floors away from what the gate actually checks against.
#
# KNOWN LIMITATION (read before assuming this closes issue #21 completely):
# package-level floors average across the WHOLE package, so the amount of
# brand-new, wholly-uncovered code a package can absorb before its average
# moves past a 0.5-point tolerance still scales with that package's total
# statement count. At today's floors, a new file needs at least:
#   - internal/cli:  15 new uncovered statements to drop it below 82.7%
#   - internal/llm:   5 new uncovered statements to drop it below 88.3%
# (computed the same way as the tolerance above: floor = covered/(total+S),
# solved for the smallest integer S that pushes coverage below the floor,
# using each package's real covered/total statement counts.) Both numbers
# are now comfortably BELOW internal/cli/planreview.go's own 53 statements
# -- so at today's tightened tolerance, this ratchet WOULD have caught that
# exact file shipping untested, with real margin. It would NOT catch
# something smaller: internal/llm's 5-statement threshold in particular is
# roughly "a single short function" -- a genuinely tiny addition can still
# slip under a large, well-tested package's average.
#
# Per-file coverage floors (checking each new/changed file's own coverage,
# not just the package average) would close this gap completely, and were
# considered. Rejected for now: it requires tracking a floor per FILE
# rather than per package, multiplying the size of this file and the
# re-baselining churn on any refactor that moves or splits code across
# files, for a benefit (catching a <15/<5-statement untested addition)
# that's already fairly narrow post-tightening. Revisit if a
# similarly-sized untested file slips through again in practice.
